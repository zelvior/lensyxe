Engineering health you can
actually verify.

Lensyxe reads your repository and scores three things: code health, dependency health, and maintainability. Same commit, same score, every time. No telemetry, no network calls, no model in the loop.

curl -sSL https://raw.githubusercontent.com/zelvior/lensyxe/main/install.sh | bash

  • 6 platforms, pure Go
  • 0 outbound requests
  • Go 1.22+ to build from source

Three dimensions. Nothing hidden.

The score is a weighted sum of three measurements. Every weight and every threshold is a constant in internal/metrics/scorer.go, and the full arithmetic is in the scoring spec.

40% Code health

File size distribution, test-to-code file ratio, and lexical complexity — branch points, nesting depth, and per-function estimates — aggregated across every language present.

Hotspots combine size, churn, and complexity. A file needs all three to be called confirmed.

30% Dependency health

Direct, dev, and transitive counts across Go, npm, Python, and Rust manifests, plus whether a lockfile is present. Drift is inferred from modification times.

Versions are counted, never resolved. Nothing is fetched to check whether a range still exists.

30% Maintainability

Churn and authorship over a configurable window, read from your own Git history. Hot files accumulate debt whether or not anyone noticed.

When a directory is not a repository, this is reported as unmeasured — never as zero.

What Lensyxe does not measure

A tool that implies it measures something it does not is worse than one that measures less. These are listed rather than omitted, because "why is there no coverage number?" is the first question anyone asks.

Code coverage
Tests are never instrumented. The test-to-code file ratio is a weaker, different signal and is not called coverage.
Build duration
Your build is never executed. Timing it would measure the machine and the CI runner as much as the code.
Vulnerability counts
A count needs a vulnerability database and a network call. Neither is attempted.
Lockfile staleness
Inferred from modification times. It never checks whether a pinned version still resolves.
Complexity for declarative files
YAML and SQL conditionals are mapping keys, not branches. Excluded rather than estimated.
Per-package Git signals
Churn is not attributable to a directory. Reported at the repository level.

The full list, with the reasoning behind each omission, is in the scoring spec.

Install

One static binary. No runtime, no daemon, no configuration to write before the first run.

Script recommended

Downloads the archive for your platform, verifies the published SHA-256, and installs to a directory already on your PATH.

curl -sSL https://raw.githubusercontent.com/zelvior/lensyxe/main/install.sh | bash

Pin a version with LENSYXE_VERSION=0.3.0, or choose an install prefix with LENSYXE_PREFIX=$HOME/.local/bin.

Download

Every release carries archives for six targets plus a checksums.txt.

curl -sSLO https://github.com/zelvior/lensyxe/releases/latest/download/lensyxe-linux-amd64.tar.gz
sha256sum -c checksums.txt

Targets: linux and darwin on amd64 and arm64, plus windows on amd64 and arm64.

Go install

Builds from source with your own toolchain. Requires Go 1.22 or newer.

go install github.com/zelvior/lensyxe/cmd/lensyxe@latest

The module is pure Go with CGO disabled, so it cross-compiles without a C toolchain.

Check what you got

A download should still be a local tool after you run it. Confirm the version metadata, then confirm there is no network activity: 

lensyxe version
lensyxe analyze . --format json > snapshot.json

If a binary you obtained contacts a network endpoint, it is not Lensyxe. See SECURITY.md.

Commands

Six commands do the work, plus completion and help from the CLI framework.

lensyxe analyze [path]

Score a repository. --format json emits the full snapshot, which is what the editor extension and CI consume.

lensyxe compare [rev]

Diff engineering health between two commits or tags, so a regression can be attributed to the change that caused it.

lensyxe watch [path]

Re-analyze on change, debounced. Runs in the foreground and never phones home.

lensyxe history

Plot the score over recorded runs from a local SQLite history database.

lensyxe serve

Serve a local dashboard and read-only JSON API. Binds loopback only.

lensyxe version

Print version, commit, build date, Go version, and platform.

In the editor

The VS Code extension is a viewer. It runs lensyxe analyze --format json, parses the snapshot, and renders it. It holds no scoring logic of its own, so the score in the status bar cannot drift from the score in your terminal.

  • Health score in the status bar, click to re-run
  • Sidebar tree with hotspots and risks that open the file
  • Complexity and hotspot diagnostics in the editor
  • A newer analysis supersedes an in-flight one, so saves never queue
git clone https://github.com/zelvior/lensyxe.git
cd lensyxe/ide/vscode && npm install && npm run package
code --install-extension lensyxe-vscode-0.1.0.vsix

Every release attaches the packaged VSIX, so no Node toolchain is required. See the extension guide.

Local-first, and checkable

The privacy claim is a property of the code, not a promise in a policy document.

No telemetry

There is no analytics code path in the binary. No events are queued, because there is nowhere to queue them.

No outbound requests

Analysis makes no network call at all. Manifests and Git history are read from disk. Only loopback is ever bound.

AI is opt-in and optional

An explanation layer exists behind --explain. It requires you to supply a key, and without one the tool behaves identically minus the prose.
