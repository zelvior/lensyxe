Repository health, scored deterministically.

Three measurements taken from the repository itself — code health, dependency health, and maintainability from Git history. The same commit produces the same score every time. One static Go binary. Nothing leaves the machine.

That output is from this repository, unmodified. The full report also covers languages, per-file complexity, high-churn files, dependency manifests, and every risk with its evidence.

Twenty-one seconds, and every figure in it is a real measurement. The tool computed 147 commits/week and then declined to score it, because two days of history cannot establish a cadence. Everything else it measured, it shows, with the threshold each one crossed.

How the score is built

The score is a weighted sum of three metrics. When a dimension cannot be measured its weight is redistributed rather than counted as zero, so a directory that is not a Git repository is not penalised for it.

DimensionWeightReads
Code health 40% File size distribution, test-to-code file ratio, and lexical complexity — branch points, nesting depth, per-function estimates — across every language present.
Dependency health 30% Direct, dev, and transitive counts from Go, npm, Python, and Rust manifests, plus whether a lockfile exists. Drift is inferred from modification times.
Maintainability 30% Churn and authorship over a configurable window, read from your own Git history.

A hotspot needs size, churn, and complexity together before it is called confirmed. Every weight and threshold is a constant in internal/metrics/scorer.go; the arithmetic is written out in the scoring spec.

What it does not measure

Listed because the first question about a health score is usually why there is no coverage number in it.

Not measuredInstead
Code coverage Tests are never instrumented. The test-to-code file ratio is a weaker signal and is never called coverage.
Build duration The build is never executed. Timing it would measure the machine and the runner as much as the code.
Vulnerability counts A count needs a vulnerability database and a network call.
Lockfile staleness Inferred from modification times. It never checks whether a pinned version still resolves.
Complexity for declarative files Excluded rather than estimated — conditionals in YAML and SQL are mapping keys, not branches.
Per-package Git signals Churn is not attributable to a directory, so it is reported at the repository level.
Transitive dependency risk Dependencies are counted, not analysed. No version is resolved.
Per-language scoring Complexity is aggregated across languages; a polyglot repository is scored as a whole.

The reasoning behind each omission is in the scoring spec.

Install

One static binary. No runtime, no daemon, no configuration before the first run.

Script

curl -sSL https://raw.githubusercontent.com/zelvior/lensyxe/main/install.sh | bash

Verifies the published SHA-256 before installing. Pin with LENSYXE_VERSION=0.3.0, or choose a prefix with LENSYXE_PREFIX=$HOME/.local/bin.

Release archive

curl -sSLO https://github.com/zelvior/lensyxe/releases/latest/download/lensyxe-linux-amd64.tar.gz

Six targets: linux and darwin on amd64 and arm64, windows on amd64 and arm64. Every release carries a checksums.txt.

From source

go install github.com/zelvior/lensyxe/cmd/lensyxe@latest

Requires Go 1.22 or newer. Pure Go, CGO disabled.

Check what you installed

lensyxe version

Analysis makes no outbound request at all. If a binary you obtained contacts a network endpoint, it is not Lensyxe — see SECURITY.md.

Commands

lensyxe analyze [path]
Score a repository. --format json emits the full snapshot that the editor extension and CI consume.
lensyxe compare [rev]
Diff health between two commits or tags, so a regression can be attributed to the change that caused it.
lensyxe watch [path]
Re-analyze on change, debounced. Runs in the foreground.
lensyxe history
Score over recorded runs, from a local SQLite database.
lensyxe serve
Serve a local dashboard and read-only JSON API. Binds loopback only.
lensyxe version
Version, commit, build date, Go version, platform.

completion and help come from the CLI framework. Every flag is listed in the CLI reference.

VS Code extension

The extension is a viewer. It runs lensyxe analyze --format json, parses the snapshot, and renders it — it holds no scoring logic, so the score in the status bar cannot drift from the score in your terminal. Newer analyses supersede in-flight ones, so saving several files does not queue several scans.

code --install-extension lensyxe-vscode-0.1.0.vsix

Every release attaches the packaged VSIX, so no Node toolchain is needed. To build it from source, see the extension guide.

Local-first

Analysis reads the filesystem and Git history and nothing else. There is no analytics code path in the binary and nowhere for events to be queued, so the claim is checkable rather than a promise in a policy document.

  • No telemetry, and no code path that could emit any.
  • No outbound request during analyze, compare, history, or watch.
  • serve binds loopback only.
  • History lives in a local SQLite file you can delete.
  • An explanation layer exists behind --explain and needs a key you supply; without one the tool behaves identically.
